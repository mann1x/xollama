# llama/runtime-pin-windows-mlx.txt
#
# The MLX runtime a Windows install takes, pinned as a published artifact and
# never built here. It is the fork's own build of upstream's MLX at the tag
# (run 37687432548, commit 2630dba7), the same 2,642 files as upstream's
# ollama-windows-amd64-mlx.zip, with MLX_CUDA_BIN_DIR and MLX_CUDNN_BIN_DIR set
# to "." so mlx.dll loads CUDA and cuDNN from its own folder. Upstream's zip
# bakes "C:/Program Files/NVIDIA/CUDNN/bin/x64" into mlx.dll: on a machine
# without cuDNN installed there, the first MLX operation that needs cuDNN
# panics and the request hangs. Measured on eleven2go (no cuDNN installed),
# 2026-10-08: upstream's zip panics on qwen3.5:0.8b; this one generates it,
# embeds with embeddinggemma-2 and creates from safetensors. mlx.dll, mlxc.dll,
# ollama_xgrammar.dll and libopenblas.dll are unsigned (upstream signs them).
#
# It is NOT inside xOllamaSetup.exe: the installer plus this archive would be
# about 2.5 GiB, over GitHub's 2 GiB release-asset cap (upstream's own
# OllamaSetup.exe leaves MLX out too). The installer DOWNLOADS it instead
# (app/xollama-mlx.iss, owner 2026-10-07), from repo/tag/asset below, and
# refuses any bytes whose sha256 is not this one. The release workflow hands
# the four values to the installer build (PKG_MLX_*).
#
#   repo          GitHub repository that publishes the archive (the fork)
#   tag           its release carrying the asset
#   asset         archive name: lib/ollama/mlx_cuda_v13/ (MLX, CUDA 13, cuDNN
#                 9 and the CUDA headers MLX compiles kernels against)
#   sha256        of the asset, checked by the installer before unpacking
#   upstream      ollama/ollama release the bytes were cut from
#   mlx, mlx_c    upstream's MLX_VERSION and MLX_C_VERSION at that release;
#                 they must equal this tree's (the plan job refuses otherwise)
#
# Moves with llama/runtime-pin-darwin.txt and the two Linux runtime pins on
# every fork sync.
