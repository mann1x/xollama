title: Changing a model's settings
---

[The settings that belong to the model](/xollama/model-settings) live in a layer
inside the model. Writing one by hand means writing a Modelfile with a `XOLLAMA`
directive holding JSON — which means knowing the field names, the value sets,
and the half-dozen rules about which settings need which others.

`xollama tweak model` knows all three.

```sh
xollama tweak model qwen3.6:latest
```

It reads what the model states now, asks about every setting with an
explanation of what each one does, drops anything the model cannot act on, and
replaces the model's config layer. Nothing else about the model changes: the
weights, template, system prompt and parameters are untouched.

## One setting, no questions

A flag with a value sets that setting and asks nothing:

```sh
xollama tweak model qwen3.6:latest --dca=on
xollama tweak model qwen3.6:latest --kv-k=kvarn4 --kv-v=kvarn4
xollama tweak model qwen3.6:latest --slots-max=8 --slots-tps-floor=12
```

The same flag with **no** value scopes the walk to that feature and leaves
everything else alone:

```sh
xollama tweak model qwen3.6:latest --dca
```

`--dca` asks the DCA questions — whether to enable it, and the chunk length.
`--slots` asks the five slot questions. Any other flag asks about itself, plus
whatever it is only meaningful beside: `--kv-k` also asks `kv.v`, because a
cache is a pair.

`--clear` removes the model's config entirely. `--dry-run` shows what would be
written without writing it, and `--json` prints the exact bytes that land in the
layer.

<Note>
  Every setting has a flag and every flag has a setting — both come from one
  table in `cmd/tweak/fields.go`, so `xollama tweak model --help` is the full
  list and cannot fall behind.
</Note>

## Choosing the GPU a model runs on

`--device-backend` asks where the model runs, and lists every device the
**server** found — backend, name, PCI ID, whether it is integrated, its memory,
and which engine serves it:

```
   devices on this server:
     CUDA NVIDIA GeForce RTX 3090 (0000:01:00.0, #0, 24.0 GiB total, 23.0 GiB free, served by opencoti)
     Vulkan AMD RADV RENOIR (ACO) (0000:18:00.0, #1, integrated, 63.0 GiB total, 60.0 GiB free, served by opencoti)

   1) CUDA
   2) Vulkan
   3) CPU
   4) unset
device-backend [unset]>
```

Only backends with a device present are offered, plus `CPU`. The next question
lists that backend's devices; pick one, or several by commas (`1,2`) to spread
the model across them. A pick is written as the device's PCI ID, the one
identity that survives a reboot or a card being added.

From a script, name the values directly — a number here is a device index, not
a menu line:

```sh
xollama tweak model qwen3.5:2b --device-backend=vulkan --devices=0000:18:00.0
xollama tweak model qwen3.6:27b --device-backend=cuda --devices=discrete
xollama tweak model nomic-embed-text --device-backend=cpu
```

A model pinned to a device that is not there is **refused**, naming what it
asked for, the backends the installation carries and the devices present. It is
never served on other hardware instead. An unpinned model is never placed on an
integrated Vulkan GPU while a discrete one is present — see
[device selection](/features/device-selection).

## Making a model a council

What a council is, its settings and what a client sees are on
[Council chat](/xollama/council). This section is about setting it with `tweak`.

A council answers every chat turn with several calls to the model:
- a planner decides whether the message needs the council at all, and answers
  a greeting directly;
- otherwise researchers investigate in parallel, then critics review the
  findings in parallel;
- a synthesizer writes the one answer the client receives.

Clients ask for the model as they would any other, and the deliberation
streams as thinking.

`--council` walks the council's settings, and `--council=on` alone takes the
tested defaults: 2 researchers and 1 critic, a random seed for every member,
a ±2 % temperature spread on researchers and critics, one round, and the
deliberation shown.

```sh
xollama tweak model qwen3.6-council:27b --council=on
xollama tweak model qwen3.6-council:27b --council-researchers=3 --council-critics=3
xollama tweak model qwen3.6-council:27b --council-critic-prompt=@critic.txt   # a prompt from a file
xollama tweak model qwen3.6-council:27b --council-charter                      # asks the charter and every role's prompt
```

Every council setting other than the switch is skipped silently in the full
walk while the council is off, because it could not apply. Named by a flag, it
is skipped with the reason. `council.polykv on` needs the opencoti engine;
`auto`, the default, uses shared KV where the engine offers it.

A council changes how a turn is answered, and barely how the model loads: its
members run on the council tag's own runner, with the model's launch settings.
The only addition is on opencoti with shared KV, where the runner reserves a
few pool seats for the council (four for one round). Like
any two tags over the same weights, a council tag and the model it is built
`FROM` do not share a runner, so alternating between them reloads. Use the
council tag for both: a trivial message is answered directly, in one extra
short call.

### How a council turn runs

- **Every member is an ordinary chat turn on the model**, served inside the
  server with the model's own template, parser and engine. Thinking is off for
  each member; the council's deliberation is the members' replies.
- **Every member's system message is empty**, then comes the conversation:
  one prefix all of them share, and the one a client's PolyKV pool is cut
  from. The charter opens the planner's route and plan requests, which the
  other members continue from. The system prompt, the client's or else the
  model's, goes to the synthesizer only, as a message after its own role
  prompt, and to the planner's direct answer. The members that answer the
  user know what the user expects; the others research and review without
  the answer's format rules.
- **Each parallel member has its own engine session**, named after the
  conversation's (`<session>~researcher-1`, `~critic-2`, `~synthesizer`), so
  members never wait on one slot. The planner keeps the conversation's own
  session: a direct answer is served from the same cache a plain chat would use.
- **Thinking** carries the plan, the findings and the critiques, one member at
  a time under a `### Researcher 2`-style heading: the member speaking streams
  line by line, and a parallel member's text follows it whole.
  A request with `think: false` gets the answer alone, as does
  `council.show_deliberation off`.
- **Tools or a `format`** in the request mean the client is steering the
  model's output itself, so that turn is answered as a plain chat, without the
  council.
- **Parallel members need parallel slots.** On opencoti a council runs its
  researchers and critics at once, including on Qwen3.5, Qwen3-Next, LFM2 and
  Nemotron-H: the single-sequence rule upstream applies to those architectures
  is stock llama.cpp's (see [dynamic slots](/xollama/slots)). On stock llama.cpp
  they take turns.
- **On opencoti, members share the conversation's cache** (`council.polykv`
  `auto` or `on`). The conversation is cached once, the researchers share it
  plus the plan, and the critics and the synthesizer share each further step.
  Each member computes only the part that is new to it. Measured on a 27B
  model, a council turn computed about 525 prompt tokens instead of 3,100, and
  held about 40 % less cache. The saving grows with the length of the
  conversation. When the turn ends, the shared parts are freed and the
  members' sessions closed. The conversation keeps its window for the next
  turn.
- **The conversation's window follows the engine's pressure.** If other
  requests are being refused, an idle council gives back the part of its
  window it is not using, down to `council.context.floor`. When the pressure
  clears, the next turn takes the window back. Past
  `council.context.compact_at` of the window (0.85 by default), the older
  turns are folded into a summary in front of the recent ones (see
  [Long conversations](/xollama/council#long-conversations)).
- **Watching it:** `GET /api/engine?model=<council>&endpoint=kv` shows the
  window and the pressure, and `endpoint=polykv/pools` the shared parts during
  a turn (see [Seeing what the engine did](/xollama/introspection)).

## Pinning a drafter's driver

A drafter is attached at build time with a `DRAFT` line, and its driver is
normally inferred from the drafter's own metadata — a gemma-4 assistant head
declares `requires_target_arch`, which resolves to `draft-assistant` without
anyone saying so:

```
FROM  gemma-4-A4B-98e-v9-agentic-it-Q4_K_M.gguf
DRAFT gemma-4-26B-A4B-it-assistant-Q8_0.gguf
PARAMETER draft_num_predict 3
```

`--spec-type` overrides that inference, for a head built into the target as much
as for an attached file:

```sh
xollama tweak model gemma4-98e-v9-agentic:q4km-drafter --spec-type=draft-assistant
xollama tweak model gemma4-98e-v9-agentic:q4km-drafter --spec-type=unset   # back to inferring
```

<Warning>
  A pin is an override, so it is able to be wrong. Pinning `draft-mtp` on a
  gemma-4 assistant drafter reaches the engine and the load then fails with
  `Gemma4Assistant requires ctx_other to be set`. Leave it unset unless you know
  the inference is wrong for your drafter.
</Warning>

`draft_num_predict` is deliberately **not** here — it is an ordinary
`PARAMETER`, settable per request like any other.

`xollama show` prints what the next load will actually use, and says where the
answer came from:

```
  Drafter
    source          attached
    architecture    gemma4-assistant
    parameters      419.71M
    quantization    Q8_0
    spec type       draft-assistant (inferred)
```

`(pinned)` in place of `(inferred)` means the driver came from
`draft.spec_type` rather than from the drafter's own metadata. A head built
into the weights shows `source built-in` and no file details. A model with no
drafter prints no block at all.

## Driving it from a script

The prompts are plain lines, each ending in a token that names the setting:

```
dca [unset]>
kv-k [q8_0]>
write [y/N]>
```

The name is the flag name, and the bracket holds the current value, which is
also what a blank answer keeps. Answers may be the menu number or the value
itself, so `2` and `llamacpp` do the same thing. That makes the whole walk
drivable with `expect`:

```expect
spawn xollama tweak model qwen3.6:latest --dca
expect "dca \[*\]> " { send "on\r" }
expect "dca-chunk \[*\]> " { send "262144\r" }
expect "write \[y/N\]> " { send "y\r" }
```

Running out of answers stops the command without writing anything, rather than
filling in defaults nobody chose.

## Consistency

Two different things can be wrong with a configuration, and they are handled
differently on purpose.

**A setting the model cannot act on is dropped, and named.** An opencoti-only
setting on a model that pins `llamacpp`, a chunk length under a DCA switch that
is off — there is nothing to decide, the setting cannot do anything, and leaving
it in the file would read as if it did:

```
── Consistency
   dropped kv.k_swa = kvarn4: a separate sliding-window ring cache needs the opencoti engine, and this model pins llamacpp
   dropped kv.residency_mode = window: the rolling-KV residency tactic needs the opencoti engine, and this model pins llamacpp
```

During the walk the same rule shows up as a question that is skipped rather than
asked, with the reason.

**A combination where only you know which half you meant is refused.** Saying
`kv.unified` off while dynamic slots are on is a real choice between two
features, not a redundancy, so it is not resolved for you. Interactively the
refusal re-asks exactly the settings it names — not the whole walk:

```
   ! kv.k / XOLLAMA_K_CACHE_TYPE = "kvarn3" is not a cache type stock llama.cpp accepts
   the settings it names are asked again; `unset` clears one.
```

From a script the same case is an error and a non-zero exit, because there is
nobody to ask and guessing a cache type would change the model's output.

Some of these rules are **measured**, not read out of a flag table: a
sliding-window ring needs a KVarN base on both `kv.k` and `kv.v`; both halves of
the ring must be set together; and a KVarN cache needs flash attention, so
`kv.k: kvarn2` with `flash_attention: "off"` is refused here. The engine states each of those and exits
during startup, which reaches you as a model that will not load -- and the
flash-attention one reached us the ugly way, as a model that loaded at one
context length and failed at another, because the size that failed took a retry
path where `-fa auto` resolved off. Checking them
here names the setting that has to change instead.

## Starting over

A model that already has a config is offered the choice before any questions:

```
── This model already has an xollama config
   1) modify it -- every question starts from what is there
   2) start from scratch -- every question starts unset
   3) clear it -- remove the config entirely and write nothing else
   4) quit -- change nothing
```

## What "unset" means

Every question offers `unset`, and it is not the same as `off`. A setting the
model does not state falls through to the server's environment variable, which
the prompt names:

```
   current: not set, so XOLLAMA_DCA decides
```

That is what makes a partial config safe to publish: a model says only what it
actually needs, and everything else follows the machine it lands on. See
[which setting wins](/xollama/model-settings#which-setting-wins).

## Checking it applied

```sh
xollama show qwen3.6:latest
```

```
  xOllama
    kv.k              q8_0
    kv.v              q8_0
    dca.enabled       on
    dca.chunk_size    32768
```

The section appears only when the model states something, and lists only what
it states. Settings are resolved at load time, so a change needs the model
reloaded before it takes effect. [Seeing what the engine did](/xollama/introspection) shows what
the running model was actually given.

## The server's own settings

`xollama tweak server` sets what belongs to the server rather than to a model:
defaults for every model's settings, and the
[local API key](/xollama/api-key) (`--api-key=generate|set|remove|status`, or
`--api-key` to be asked). With no flag it asks which part to change.

### Defaults for every model

Every `tweak model` setting that is not a model's own can be given a
server-wide default: engine, flash attention, KV cache types, unified KV, the
residency tactic, slots, session pooling, and the drafter's speculative type.
The flags are those of `tweak model`, and the walk and the consistency pass are
the same:

```shell
xollama tweak server --kv-k=q8_0 --kv-v=q8_0 --slots=on --slots-max=4
xollama tweak server --slots          # walk only the slot settings
xollama tweak server --clear          # remove every default
```

- **The model wins.** A model that states a setting keeps it; the server's
  default fills only what the model leaves unset. Then come the environment and
  the built-in default. Within the KV section a model's cache pair stays a pair:
  a model that states `kv.k` does not get the server's `kv.v`.
- **A default a model cannot use is left out.** A KVarN cache for a model
  pinned to stock llama.cpp, for example. The server leaves that section out
  for that model and logs it, rather than refusing to load the model.
- **Not the model's own settings.** DCA, the device pin and the council
  describe a model. They are not offered as server defaults.
- A default applies at a model's next load. The command offers to unload the
  running models (`-y` unloads them without asking).

`xollama tweak show model NAME` lists the settings a model runs with and marks
each one `model` or `server`, so you can see which ones come from the server.

## Environment variables, without the environment

Upstream configures a server through environment variables. Changing one means
editing the global environment or a systemd override, looking up the name, and
restarting. `xollama tweak envs` sets the same variables in the server's own
settings file instead (`~/.ollama/xollama-settings.json` in the server's home):

```shell
xollama tweak envs OLLAMA_KV_CACHE_TYPE=q8_0 XOLLAMA_MAX_PARALLEL=4
xollama tweak envs --unset OLLAMA_KV_CACHE_TYPE
xollama tweak envs        # ask, one variable at a time
```

- **The settings file wins.** A value set here beats the same variable in the
  environment, under either spelling (`OLLAMA_` or `XOLLAMA_`). `xollama tweak
  show envs` names any environment value an override replaces, so nothing is
  hidden. Remove the override, and the environment applies again.
- **Most changes apply at once.** A variable read at load time, such as the
  KV cache type or the slot settings, applies at the next model load. The
  command offers to unload the running models (`-y` unloads without asking).
  A few variables are read only when the server starts: the listen address,
  the models directory, origins, GPU visibility and the proxies. For those the
  command says that a restart is needed.
- **Variables for the engines are passed on.** `LLAMA_ARG_*`, `OPENCOTI_*`,
  `CUDA_VISIBLE_DEVICES` and the other GPU-runtime variables reach every engine
  the server starts, as if they were in its environment.
- **Not the API key.** `XOLLAMA_API_KEY` is refused: `tweak server --api-key`
  keeps only the key's digest on disk.
- **Only from the server's own machine.** Changes are accepted from the
  server's own machine only, never through a proxy, and with the key while
  one is set.

## What is set, and where it comes from

```shell
xollama tweak show envs            # the variables with a value, and their source
xollama tweak show envs --all      # every variable, at its default too
xollama tweak show server          # the API key, the defaults and the variables
xollama tweak show model qwen3:8b  # what the model runs with, model or server
```

## The server's GPUs

`xollama tweak server gpu` sets which GPUs models may use, in what order,
through which backend, at what link speed, and whether a model is split:

```shell
xollama tweak server gpu                                 # ask
xollama tweak server gpu 0000:01:00.0 --priority 10      # first choice
xollama tweak server gpu 0000:02:00.0 --disable          # keep models off it
xollama tweak server gpu 0000:01:00.0 --backend CUDA     # it is also a Vulkan device
xollama tweak server gpu 0000:01:00.0 --link 4x16        # plan with PCIe 4.0 x16
xollama tweak server gpu --split single                  # never split a model
```

- **Priority is fill order.** A model that fits on one GPU goes to the
  highest-priority GPU with room, instead of the one with the most free
  memory. A split fills the GPUs in priority order.
- **A model's own device pin wins.** A model that pins GPUs with
  `tweak model --devices` keeps them, even a disabled one.
- **Link speed.** opencoti plans the KV rolling window with the host link
  speed, which it probes when a model loads. A host that is busy at that moment
  gets a wrong reading for the whole session, and a forced figure skips the
  probe. Set it as GB/s, as a PCIe generation and lane count (`4x16`, or the
  generation and lanes wizard), or as `auto`. The engine takes one figure per
  process, so a load spread over several GPUs uses the slowest forced figure
  among them.
- **Split** is `auto` (split only a model too large for one GPU, or follow
  `OLLAMA_SCHED_SPREAD`), `spread` (always split) or `single` (never: what
  does not fit stays on the CPU).
- **Split mode** is `layer`, the default and the one validated on every
  opencoti path, or `row`. `row` is CUDA only and not yet validated with
  opencoti's KV paths; on Vulkan it becomes `layer`.

Changes apply at a model's next load. `xollama tweak show server` lists the
GPUs with their settings.
